# Non-LLM tooling, SDK/C++ handling and "done" policies in DS (mwccarm) matching decomps

Scope: tools and techniques that DS/CodeWarrior matching projects use to finish hard functions and structural gaps, for FFC (mwccarm DSi 1.2p2 = build 1028, dsd, wibo, relocation-exact compare). Research date 2026-10-16. Most facts were read directly from shallow clones of the repos (HEAD dates noted); URLs point to the repo root or file path on GitHub.

Repo snapshots read: simonlindholm/decomp-permuter (HEAD 2026-10-06), AetiasHax/ds-decomp v0.12.1 (HEAD 2026-09-20), encounter/objdiff 3.8.2 (HEAD 2026-09-29), matt-kempster/m2c (HEAD 2026-09-16), decompme/decomp.me (HEAD 2026-10-14), ethteck/coddog, pret/pmd-sky (2026-10-14), pret/pokeplatinum (2026-10-14), ntrtwl/NitroSDK (2026-10-04), zeldaret/ph, sturmds/advance-wars-dual-strike-decomp (2026-10-15), Yokimitsuro/khdays-decomp (2026-10-11), tangosdev/sm64ds-decomp (2026-10-16), tangOS-decomps/pictochat-decomp (2026-10-03).

## 1. decomp-permuter: arm32 + mwcc support, success on regalloc near misses, run time, DS usage

### Takeaway
Upstream decomp-permuter supports ARM32 and has an `[mwcc]` weight table, so it runs on mwccarm with a compile script (wibo) and an ARM objdump. The best DS evidence comes from Advance Wars DS (same dsd/mwcc stack). On 37 functions that agents had parked after 2-6 failed retries, a 600 s run each matched 9 (24%) with no model tokens. Every match came within 3 minutes. sm64ds got only one or two cracks, and pictochat logged clean negatives. It works for register-only and small-ordering residues. It does not fix structural misses, and its output must be rewritten by hand.

### Cited Findings
- README: "This tool supports MIPS (compiled by IDO, possibly GCC), PowerPC, and ARM32 assembly"; `-j` for multithreading; input dir = one-function .c, target .o, compile .sh, settings .toml; `import.py` works with Ninja if `permuter_settings.toml` has `build_system = "ninja"`. — [decomp-permuter README](https://github.com/simonlindholm/decomp-permuter)
- Code: `src/objdump.py` defines `ARM32_SETTINGS` (name "arm32", `R_ARM_` relocs, executable `arm-none-eabi-objdump`, ARM branch/cond tables); `default_weights.toml` has `[base]`, `[ido]`, `[mwcc]`, `[gcc]` tables chosen by `compiler_type` in settings.toml; `ast_util.py` supports MWCC-specific `u32 var : 0x1234;` syntax. — [decomp-permuter src](https://github.com/simonlindholm/decomp-permuter/tree/main/src)
- Author on scope: "generally best towards the end, when mostly regalloc changes remain. If there are reorderings or functional changes ... neither the scorer nor the randomizer tends to play well with them"; "The randomization mode often finds lots of nonsensical changes that improve regalloc 'by accident'"; stack positions ignored unless `--stack-diffs`. — [README](https://github.com/simonlindholm/decomp-permuter)
- PERM macros (`PERM_GENERAL`, `PERM_LINESWAP`, `PERM_RANDOMIZE`, `PERM_IGNORE`/`PERM_PRETEND` for C++/non-C) restrict and steer the search. pycparser means C only, and C++ needs `PERM_IGNORE`. — [README](https://github.com/simonlindholm/decomp-permuter)
- **Advance Wars DS (dsd + mwcc 2.0-72, same pipeline as FFC):** `tools/permuter.py --parked`, 600 s/function, 4 jobs at `nice -n 19`. 37 of 43 parked functions were run. Results: **9 matched and landed**, 3 got closer, 7 got closer only through behaviour-changing or dead code (logged as hints, not applied), and 18 did not change. "9 matches in 37 functions that agents had retried two to six times, with no model tokens. Every match came within 3 minutes (3 s to 166 s); no function improved after the first few minutes." — [AWDS docs/issues/0052-partials-strategy.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/issues/0052-partials-strategy.md)
- AWDS fix types the permuter found, rewritten as plain C: an unsigned operand or `(u32)` index cast (3 matches); a value read once into a local used twice; a sum split into two steps; moving a counter increment to the end of the loop body; an empty `if (a && b)` after a call that changes loop layout. — same source
- AWDS integration details: the permuter is pinned at commit `059609d4aec7` and needs `arm-none-eabi-objdump`. The scorer was changed in two ways: (1) disassemble only the named function; (2) rewrite each relocation as symbol address plus addend, because dsd's object and the compiled object name the same address differently (`data_ov000_022dbd7c` vs `Ov000_gMapHeaders+0x54`), which otherwise added "a constant penalty to every score". Input is C after `mwccarm -E`. `asm` declarations are hidden from the parser. — same source; [AWDS docs/workflow.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/workflow.md)
- AWDS retry economics (136 partials, 211 model retries, ~6.1M tokens): retry 1 matched 47%, retry 2 16%, retry 3 10%, retry 4 0%. Near misses ≥99.5% were the worst bucket (20%, 142k tokens per match). The rule adopted was "park after two failed retries", which would have lost 2 of 74 matches and saved 13% of tokens. A pragma sweep (`tools/pragmas.py`: every `#pragma optimization_level`, `opt_*` and peephole on/off, at file or function scope, then pairs and triples) matched 8 functions at ~2k tokens each. — [AWDS 0052](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/issues/0052-partials-strategy.md)
- AWDS `permute.py` (based on khdays `declperm.py`): it tries declaration order exhaustively up to 120 orders, then hill-climbs, adjacent statement swaps and local types. It found declaration orders for a few matches but "on a register-only diff it never found one alone". The real permuter matched a register-only function parked after 6 retries "in seconds". — [AWDS workflow.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/workflow.md)
- **sm64ds (mwccarm 1.2/sp2p3):** `func_02072fcc` (528 B) "fell to the permuter off its banked near-miss (#781)". A 420 s `-j4` pass over the 12 closest arm9 targets produced "no banks, no divergence improvements". "Seven minutes per function is too short ... Budget 25 minutes or more before believing a negative", and a 35-minute run moved a target the earlier pass had called still. The permuter "reports NOCHANGE on a base that failed to compile", so check that the base compiles. — [sm64ds notes/arm9-endgame.md](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/arm9-endgame.md)
- sm64ds "Group A" (6 functions whose C is correct but differ only in register allocation or ordering, at 2-6 instructions): both hand sweeps and the permuter failed; listed as "believed impossible at present (do not spend)", with a caveat that the permuter evidence was budget-limited. — same source
- pictochat-decomp (DSi system title, mwccarm 2.0 family): permuter runs of 300 s / 3,557 iterations and ~9,400 iterations plateaued on functions with structural divergence. The project also found a tooling bug. Seeds containing PERM macros failed to compile when relocation offsets were being detected, which baked a non-zero score floor into every run (~10,915 → ~9,745 after the fix). It uses a capstone-based `cap_objdump.py` in place of arm-none-eabi-objdump. — [pictochat notes/mwccarm-codegen.md, notes/tooling.md](https://github.com/tangOS-decomps/pictochat-decomp/tree/main/notes) (the project's notes are heavily agent-written; treat as anecdotal)
- ARM forks laqieer/decomp-permuter-arm and mparisi20/decomp-permuter-arm target "ARM/Thumb code compiled by embedded arm compilers" (GBA-oriented); upstream now has arm32 natively. — [laqieer fork](https://github.com/laqieer/decomp-permuter-arm), [mparisi20 fork](https://github.com/mparisi20/decomp-permuter-arm)

### Inferences
- For FFC's ~544 near misses ≥90%, a batch permuter pass is cheap: about 10 min/function × 4 jobs comes to roughly 1-2 CPU-days at ~$0 in tokens. AWDS suggests 10-25% of parked register/ordering misses fall to it. Restrict it to C files whose instruction count already matches, and expect most wins in the first 3 minutes. Run a longer 25-35 min tail only on functions whose score moved.
- On FFC, the reloc-name-normalizing scorer patch (AWDS) is essential: dsd-delinked targets use `data_*`/`func_*` names while our objects may use other symbols.
- FFC compiles some files as C++, but pycparser is C only. Either permute only C-mode files, or use AWDS's approach of preprocessing and hiding non-C constructs with `PERM_IGNORE`/`PERM_PRETEND`.
- A pragma sweep is a separate, nearly free lever worth running before the permuter. AWDS got 8 matches from pragmas alone.

### Gaps
- No published success rate on a large (>100) mwccarm near-miss set. AWDS n=37 is the best data point.
- AWDS's `work/permuter-run1.md` is not in the public repo; only the summary is.

## 2. coddog, asm-differ, objdiff, decomp.me, m2c, Ghidra starting points

### Takeaway
objdiff (3.8.2) is the standard relocation-aware DS differ and report generator. decomp.me has an `nds_arm9` platform with mwcc_40_1028 ("MW 1.2p2"), which is FFC's compiler. m2c has an `arm` target and an `mwcc` compiler mode, good for scaffolds on large functions. coddog is a Rust similarity finder that supports `nds_arm9`, already partly ported to FFC as an idea. Ghidra shared projects are the usual human starting point. decomp.dev, the progress hub, is being sunset.

### Cited Findings
- objdiff: supports "ARM (GBA, DS, 3DS)", ARM options include `arm.archVersion` (v4T/v5TE "DS"/v6K), function relocation diffs option (`functionRelocDiffs`), "Combine data/text sections", experimental data-flow analysis; CLI has `diff` and `report` commands; per-unit `metadata.complete`; "Detailed progress reporting (powers decomp.dev)". Version 3.8.2. — [objdiff README & config schema](https://github.com/encounter/objdiff)
- decomp.dev sunset: "the main index and adding new projects are disabled", project pages and history stay up; the site as "a public index and leaderboard is now causing more harm than good"; code not open source. — [decomp.dev](https://decomp.dev/)
- decomp.me `nds_arm9` compilers (cromper/compilers.linux.yaml): mwcc_20_56..20_87, mwcc_30_114..30_139, mwcc_40_1018, ... mwcc_40_1028; run as `${WIBO} mwccarm.exe -pragma "msg_show_realref off" -c -proc arm946e -nostdinc ...`. Labels: `mwcc_40_1028` = "4.0 build 1028 (MW 1.2p2)", `mwcc_30_131` = "3.0 build 131 (MW 2.0sp1p5)", `mwcc_30_139` = "MW 2.0sp2p4". — [decomp.me cromper/compilers.py](https://github.com/decompme/decomp.me/tree/main/cromper), [frontend compilers.json](https://github.com/decompme/decomp.me/blob/main/frontend/src/lib/i18n/locales/en/compilers.json)
- `dsd objdiff --scratch --compiler <id> --c-flags ... --preset-id` writes decomp.me scratch metadata into objdiff.json, so objdiff's "decomp.me" button creates scratches. zeldaret/ph uses `DECOMP_ME_COMPILER = "mwcc_30_131"` and a "Phantom Hourglass" preset. — [ds-decomp README](https://github.com/AetiasHax/ds-decomp), [zeldaret/ph tools/configure.py, docs/decompiling.md](https://github.com/zeldaret/ph)
- m2c: "a decompiler for 32-bit MIPS, ARM, PowerPC and SuperH ... with partial support for C++"; targets include `arm` and `gba`; compilers `ido`, `gcc`, `mwcc`. — [m2c README](https://github.com/matt-kempster/m2c)
- pictochat/sm64ds report m2c drafts are "disproportionately valuable specifically on large functions" (0x400+ bytes) as semantic scaffolds. — [pictochat notes/tooling.md](https://github.com/tangOS-decomps/pictochat-decomp/blob/main/notes/tooling.md) (anecdotal)
- coddog: "identify duplicate functions and portions of functions among one or more binaries"; commands `match` (threshold similarity), `cluster`, `submatch` (common n-length segments), `compare2`/`compare-n` across projects via decomp.yaml; source maps `"nds_arm9" => Platform::Nds` and decodes ARM/Thumb via unarm. — [coddog](https://github.com/ethteck/coddog)
- AWDS/khdays twin and family tooling: relocation-masked twin families; C copied from a matched function to its twins (`findtwin.py`, `dedupprop.py`, `genfamily.py`, `nearfam.py`, `port_template.py` → AWDS `tools/propagate.py`). Several AWDS retry matches came "against its twin". — [AWDS docs/third-party/khdays-decomp.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/third-party/khdays-decomp.md)
- Ghidra: zeldaret/ph uses a shared Ghidra project (Ghidra 11.2.1) as the decompilation starting point; khdays has `tools/ghidra`, `gen_ghidra_twin.py`; pictochat `ghidra_batch.py`/`ghidra_draft.py`. — [ph docs/decompiling.md](https://github.com/zeldaret/ph/blob/main/docs/decompiling.md), [khdays tools](https://github.com/Yokimitsuro/khdays-decomp/tree/main/tools)
- sm64ds `tools/linkcheck.py`: the match gate wildcards relocated words, so it cannot see where a relocation points. linkcheck writes the resolved target into each relocation slot with real ARM encoding and byte-compares, catching wrong callees or globals. It treats veneers (`LDR ip,[pc]; BX ip; .word real`) and byte-identical twins as benign. — [sm64ds notes/link-verification.md](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/link-verification.md)

### Inferences
- FFC can share hard cases on decomp.me with exact-compiler fidelity (mwcc_40_1028) for human help.
- With decomp.dev sunsetting, objdiff `report` JSON stays useful locally but no longer as a public leaderboard.

### Gaps
- asm-differ ARM support was not verified in this pass. From memory it has an arm32 arch, but this is unverified.
- No benchmark comparing m2c ARM output quality on mwccarm code.

## 3. dsd (ds-decomp) features and adding missing functions/vtables

### Takeaway
dsd v0.12.1 provides rom extract/build, `init` auto-analysis, `delink`, `dis`, `objdiff`, `lcf`, `check modules`/`check symbols`, `apply` (ELF symbols back into symbols.txt), `sig apply/list`, `format`, and `diff new/apply` (import improved analysis from newer dsd). Its function discovery is a linear sweep that stops at data pointers and runs call-target passes. Functions reached only through vtables can be missed, and are added by hand as `kind:function(arm,size=…)` lines in symbols.txt.

### Cited Findings
- Commands: `rom extract|build|config`, `init`, `delink`, `dis`, `objdiff` (`--scratch`, `--compiler`, `--c-flags`, `--preset-id`, `--custom-make`), `lcf`, `json delinks`, `check modules` ("Verifies that built modules are matching the base ROM"), `check symbols` ("all symbols from every symbols.txt exist in the final linked ELF"), `apply` ("Applies symbol data from the final linked ELF to symbols.txt"), `sig apply`/`sig list`, `format`, `diff new` (compare two dsd projects to bring "improved analysis results of newer dsd versions to old dsd projects", with `--skip-*` filters) and `diff apply` (TUI). — [ds-decomp README](https://github.com/AetiasHax/ds-decomp)
- Signatures: the repo ships only `assets/signatures/FS_LoadOverlay.yaml` and `FS_UnloadOverlay.yaml`. It is not a general SDK signature library. — [ds-decomp assets/signatures](https://github.com/AetiasHax/ds-decomp/tree/main/assets/signatures)
- delinks.txt: section kinds `code|data|rodata|bss`; per-file sections `.text/.rodata/.init/.ctor/.data/.bss`; file option `complete` makes `dsd lcf` link the built object instead of the delinked one; "dsd lcf will handle the link order automatically". — [docs/delinks.md](https://github.com/AetiasHax/ds-decomp/blob/main/docs/delinks.md)
- symbols.txt kinds: `function(arm|thumb,size=0x…,unknown)`, `label`, `data(byte[256]|any|word…)`, `bss(size=…)`; attributes `local`, `weak`, `ambiguous` (resolves relocations that can lead to multiple overlays). — [docs/symbols.md](https://github.com/AetiasHax/ds-decomp/blob/main/docs/symbols.md)
- Function discovery (`lib/src/analysis/functions.rs`): sequential sweep from section start that skips illegal patterns and runs of ≥8 pointer-like words. It uses pool constants that point to data as upper bounds. It handles trampolines, DS Protect size overrides and encrypted ranges. `Module::find_undiscovered_functions` then repeats analysis on call destinations "until there are no function calls leading to undiscovered functions"; `.ctor` analysis (`ctor.rs`) locates the static-initializer list from the entrypoint's last call. — [ds-decomp lib/src](https://github.com/AetiasHax/ds-decomp/tree/main/lib/src)
- zeldaret/ph (C++, dsd v0.11.0, mwcc 2.0/sp1p5, wibo 0.6.16, objdiff 3.4.0) has `tools/vtable_sym.py` to "Define vtable symbols and update relocations" across all symbols.txt files. Its configs name 564 `__sinit_*` functions plus `.p__sinit_*` `.ctor` pointer entries. — [zeldaret/ph tools/vtable_sym.py, config/usa](https://github.com/zeldaret/ph)
- AWDS `tools/scan_pointers.py` finds 4-byte words in .data/.rodata and literal pools that look like addresses but have no relocation, ranked layout/high/medium. "high" means the value is the start of a known symbol (or a Thumb address + 1) next to another relocated word, i.e. a pointer table. — [AWDS tools/scan_pointers.py](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/tools/scan_pointers.py)
- AWDS counts "code in dsd gap units that has no function" (issue 0071) as code bytes. AWDS `tools/data.py` and `tools/bss.py` define every `.data`/`.rodata`/`.bss` object in C so the data links from `complete` files. Values come from the builder's ROM through generated `inc.c` files, and `symbols.txt` sizes are written so objdiff compares equal sizes. — [AWDS docs/data-tool.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/data-tool.md), [bss-tool.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/bss-tool.md)
- AWDS bss-tool note: "mwccarm 2.0 puts each data or .bss variable of a file in its own section", and make check pins only addresses that something points to. — [bss-tool.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/bss-tool.md)

### Inferences
- FFC's ~500 vtable-only ov002 functions: dsd's sweep likely stopped at a data-pointer upper bound or a parse failure, and no `bl` reaches those functions. The fix is a scan of .data words that point into .text, as in vtable tables (AWDS scan_pointers "high" tier), then adding `name kind:function(arm,size=…) addr:…` lines and re-delinking. arcnid's symbol list can be the seed. dsd `diff new/apply` could also pull improved analysis from a newer dsd init.
- Unresolved tail-call targets (0x0216b128, 0x021553c4) are the same problem: add the function symbols by hand.

### Gaps
- Not verified whether dsd 0.12.x improves vtable or data-pointer function discovery compared with the version FFC used.

## 4. SDK/NitroSDK/TWL-SDK/MSL handling, inline asm, C++ (vtables, __sinit, thunks)

### Takeaway
Projects share SDK source: ntrtwl's NitroSDK/NitroSystem/NitroWiFi/NitroDWC repos are pulled in as Meson wraps by pokeplatinum, and khdays identified 979 SDK functions by compiling pret/pokediamond's NitroSDK source. No public TwlSDK decomp was found. All DS projects reviewed write SDK sysreg/BIOS/CP15 code as mwcc `asm void f(){…}` functions in .c files and count them as complete. For C++, `__sinit_*` is written as C/C++ static initialisers, or as an explicit `__sinit_*` C function matched per symbol. this-adjust thunks are compiler-emitted from class definitions with multiple inheritance, or kept as asm shards.

### Cited Findings
- ntrtwl org repos: NitroSDK, NitroDWC, NitroWiFi, NitroSystem, libvct (all C; updated Sep-Oct 2026); no TwlSDK listed. — [github.com/ntrtwl](https://github.com/ntrtwl)
- pokeplatinum `subprojects/*.wrap`: NitroSDK (dir `NitroSDK-4.2.30001`), NitroSystem (`071126.1`), NitroWiFi (`2.1.30003`), NitroDWC (`2.2.30008`), libvct, pinned by git revision. — [pokeplatinum subprojects](https://github.com/pret/pokeplatinum/tree/main/subprojects)
- pmd-sky vendors `lib/NitroSDK` (48 .c + 46 .s), `lib/MSL_C`, `lib/NitroDWC`, `lib/syscall`. — [pret/pmd-sky lib](https://github.com/pret/pmd-sky/tree/main/lib)
- ntrtwl/NitroSDK writes system-register functions as mwcc asm functions in .c, e.g. `asm void OS_SetExceptionVectorUpper(void) { mrc p15, 0, r0, c1, c0, 0 ... }`, `asm void OS_EnableICacheForProtectionRegion(register u32 flags)`, `static asm void init_cp15(void)`. 38 .c files contain asm functions. — [ntrtwl/NitroSDK libraries/os/src](https://github.com/ntrtwl/NitroSDK)
- khdays: "Identifies NitroSDK functions ... by compiling reference SDK source (from pret/pokediamond) with our matching mwccarm 3.0_patch4 toolchain and searching the produced bytes". Reloc-free functions are matched exactly; functions with calls are matched with relocations masked. "979 unique func_XXXXXXXX named (~4.2% of the 23,240 ROM functions)". — [khdays sdk/README.md](https://github.com/Yokimitsuro/khdays-decomp/blob/main/sdk/README.md)
- Inline assembler dialect (mwccarm): no `.word`, use `dcd`, `ldconst rX, #imm`, `lda rX, symbol`; no `.section`; comments C-style. — [zeldaret/ph docs/inline_assembler.md](https://github.com/zeldaret/ph/blob/main/docs/inline_assembler.md)
- sm64ds asm policy: "Assembly counts as matched only when assembly is what the original source contained". The objective test is instructions C cannot express: `mcr/mrc`, `swi`, `msr/mrs`, `ldm/stm ^`, `swp/swpb`. On 2026-07-24, 116 whole-function asm blocks were reclassified NONMATCHING; 35 SDK/BIOS routines (Div, CpuSet, CpuFastSet, ARMSave/RestoreContext, Sqrt, Halt, IntrWait, CP15 cache ops) stayed matched, and 10 more were restored on audit. Whole-function `dcd 0x…` dumps are "vacuous" matches and fail PR validation. — [sm64ds notes/asm-policy.md](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/asm-policy.md), [tools/asm_policy.py](https://github.com/tangosdev/sm64ds-decomp/blob/main/tools/asm_policy.py)
- AWDS `config/AWRE/asm_functions.txt`: 252 lines of asm functions counted as decompiled. Each must match, and its file must have portable C or `#error` in the `#else` of `#ifdef __MWERKS__`, with a stated reason. Reasons include: branches into shared NaN/trap tails (46), swi BIOS stubs (43), long-division shared push (15), mrs/msr CPSR (14), mcr/mrc CP15 (12+8), soft-float arg pushes (8), ldm/stm block kernels or copies (6+5), clz in the IRQ handler, swp/swpb, "ldr+bx alias stub; mwcc emits b". — [AWDS config/AWRE/asm_functions.txt](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/config/AWRE/asm_functions.txt)
- khdays progress policy: library functions originally written in assembly (NitroSDK asm cache/protection/interrupt/context switch, memcpy/fill kernels, matrix helpers, DGT SHA-1, BIOS SWI veneers, CW runtime long-long/division helpers, MobiClip routines) are "complete" when integrated under `libs/**/asm_stubs/` (inline `asm` in .c, or GAS `.s` where routines branch into each other) and listed with source evidence in `report_asm_matches.json`. "They are still not counted as C ... game code has no such exception", except 2 game functions needing `clz`. — [khdays docs/PROGRESS_POLICY.md](https://github.com/Yokimitsuro/khdays-decomp/blob/main/docs/PROGRESS_POLICY.md)
- C++ static initialisers: "at most one static initializer per source file"; global objects initialised by a constructor generate `.init` code and a `.ctor` entry automatically. Main LCF order is `.text | .init | .rodata | .ctor | .data | .bss | .sbss`, and for overlays `.init` comes after `.rodata`. — [zeldaret/ph docs/build_system.md](https://github.com/zeldaret/ph/blob/main/docs/build_system.md)
- sm64ds writes `__sinit_*` as standalone C functions (60 files, e.g. `src/unnamed/ov002/__sinit_ov002_02100f84.c`, `void __sinit_ov002_02100f84(void) { data_…[0] = 0; …; func_020731dc(…); }`) matched per symbol. A pilot proved `__sinit_ov002_02100938` belongs to the `dEnemyBase_c` TU and is generated by two eight-element arrays of pointer-to-member functions. — [sm64ds src/unnamed/ov002](https://github.com/tangosdev/sm64ds-decomp/tree/main/src/unnamed/ov002), [notes/sinit-ownership-pilot-ov002.md](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/sinit-ownership-pilot-ov002.md)
- sm64ds this-adjust thunks (`_ZThn80_N9ModelAnimD0Ev` = "non-virtual thunk adjusting this by -80"): in BlendModelAnim.cpp, "the two `_ZThn80_` destructor thunks stay enrolled shards: defining the key function ~BlendModelAnim() would emit the whole MI vtable group into this object, and the secondary table's preamble lands inside the primary's compared extent". The same file notes "mwccarm emits .text in reverse source order under default deferred codegen". — [sm64ds src/engine/model/BlendModelAnim.cpp](https://github.com/tangosdev/sm64ds-decomp/blob/main/src/engine/model/BlendModelAnim.cpp), [notes/cpp-naming-guide.md](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/cpp-naming-guide.md)
- pmd-sky NONMATCHING fallback: `#ifdef NONMATCHING <C> #else asm void ov11_022EC27C(...) { stmdb sp!, {...} ... } #endif` (6 NONMATCHING sites). It also has a `tools/asm_processor` (`GLOBAL_ASM`) path. — [pret/pmd-sky src/ground_bg.c](https://github.com/pret/pmd-sky/blob/main/src/ground_bg.c), [common.mk](https://github.com/pret/pmd-sky/blob/main/common.mk)

### Inferences
- FFC's 71 system-register SDK functions are in the category every surveyed DS project (sm64ds, AWDS, khdays, pmd-sky, NitroSDK itself) writes as `asm void` and counts as complete. Changing FFC's policy from swi-only to the sm64ds instruction test (`mcr/mrc/mrs/msr/swi/swp/ldm^`) would follow community practice. This is the human decision LONGTAIL_PLAN already flags.
- FFC's 163 `__sinit` functions: sm64ds shows a cheap middle path. Write each `__sinit_*` as an explicit C function that stores into extern globals and calls ctors, matched per symbol, without full class TUs. Full fidelity, with automatic `.init` and `.ctor` emission, needs data-section TU support as in ph/AWDS.
- FFC's 141 thunks: these are emitted only when the class with the vtable is defined in the TU. sm64ds leaves them as asm shards when emitting the vtable group would break other comparisons. A realistic interim is a separate category such as "compiler-generated, pending class TU" rather than a matching target.
- SDK identification: compiling ntrtwl/NitroSDK (or pret/pokediamond lib) with mwcc 1.2p2 and byte-matching, as khdays does, could name and auto-match SDK functions, though FFC's DSi SDK (TWL) versions will differ.

### Gaps
- No public TwlSDK (DSi SDK) decomp was found. Overlap with NitroSDK sources for FFC's SDK parts is unknown.
- Exact mwccarm rules for when this-adjust thunks are emitted, and where, were not documented in any source found.

## 5. Policies on "done": NONMATCHING / asm fallback / 100% linked

### Takeaway
Two DS projects on FFC's stack report 100%. khdays reports 23,231/~23,233 functions complete, with 99.5% real C and 108 asm. AWDS reports 8,571/8,571 functions and 100% of code linked, with asm counted only via an allowlist. Both publish separate C-only and asm categories. pret DS repos keep `#ifdef NONMATCHING` C next to an asm fallback. sm64ds and pictochat keep NONMATCHING drafts uncounted.

### Cited Findings
- khdays (EU YKGP, mwccarm 3.0 build 139): "Every function of the EU ARM9 program and its overlays is matched ... byte-identical (306 of 306)"; "All of the game's own code is C except two functions that need the clz instruction"; real C 23,125/~23,233 (99.5%); real C bytes 99.73%; inline asm/stub 108; initialized data 188,336/188,340. — [khdays README](https://github.com/Yokimitsuro/khdays-decomp)
- AWDS: Code decompiled 100%, Code linked 100% (1,845,012 bytes), functions 8,571/8,571, data linked 99.9991%. "Functions written as asm count only when config/AWRE/asm_functions.txt lists them." Each commit must pass `make release` (build, `make check` module-by-module and whole, format). — [AWDS PROGRESS.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/PROGRESS.md), [README](https://github.com/sturmds/advance-wars-dual-strike-decomp)
- AWDS parking rule: "Park a function after two retries that did not match it", recorded with best attempt, triage class and reopen conditions (a twin matches, a no-token pass gets within 2 instructions, a prototype/struct changes, a new cookbook line fits). — [AWDS docs/workflow.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/workflow.md)
- pmd-sky: contributions "must maintain a matching ROM" (`make` prints `pmdsky.us.nds: OK`). — [pmd-sky CONTRIBUTING.md](https://github.com/pret/pmd-sky/blob/main/CONTRIBUTING.md)
- sm64ds: ~98% of functions, ~91% of code bytes (org profile claim). NONMATCHING files do not count. — [tangOS-decomps profile](https://github.com/tangOS-decomps), [sm64ds asm-policy](https://github.com/tangosdev/sm64ds-decomp/blob/main/notes/asm-policy.md)
- pictochat: "1048 / 1551 functions matched (67.6%) ... (15 more parked NONMATCHING - logic-correct, not byte-exact)". — [pictochat README](https://github.com/tangOS-decomps/pictochat-decomp)

### Inferences
- A FFC "done" definition could follow khdays/AWDS: (a) real-C matched; (b) asm-complete via an allowlist with a reason per instruction (sysreg/swi/clz/hand kernels); (c) NONMATCHING C plus an asm fallback (pmd-sky style) to reach "100% linked" without inflating the C count.

### Gaps
- Neither khdays nor AWDS is heavy C++. ph and sm64ds (both C++) are not at 100%, so no C++ DS project has shown a full thunk/sinit solution.

## 6. Build speed tricks

### Takeaway
Projects use ninja with per-object rules, native-Linux mwcc (metroskrew) instead of wine/wibo, pinned tool downloads, fast per-function checkers that avoid a full link, and running permuter/sweeps under `nice` in parallel with agents.

### Cited Findings
- AWDS runs "the Metrowerks compiler and linker ... through metroskrew, whose binaries are 32-bit", "relinked as native Linux ELF binaries. The files keep their .exe names but need no wine". `tools.lock` pins metroskrew 0.1.3 (`github.com/mid-kid/metroskrew/releases/download/0.1.3/metroskrew-linux.tar.xz`), dsd 0.12.1 and objdiff-cli 3.8.2 with SHA-256. — [AWDS tools.lock, README](https://github.com/sturmds/advance-wars-dual-strike-decomp)
- AWDS fast checks: `build/fnindex.json` plus `tools/fn.py check` (a positional compare without a full link). `triage_partials.py` takes about 10 minutes with 3 jobs. — [AWDS 0052](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/issues/0052-partials-strategy.md)
- zeldaret/ph: `configure.py` writes build.ninja, runs mwcc via wibo (`-w` path) plus sjiswrap, and `transform_dep.py` converts dependency files for incremental rebuilds. — [ph tools/configure.py](https://github.com/zeldaret/ph/blob/main/tools/configure.py)
- khdays changes alignment by turning every `ALIGNALL(4)` into `ALIGNALL(2)` (`tools/_run_mwld.py`, `patch_align.py`); AWDS changes only the objects that need it. — [AWDS docs/tool-issues.md](https://github.com/sturmds/advance-wars-dual-strike-decomp/blob/main/docs/tool-issues.md)
- pictochat: on Windows the permuter's `-j` workers orphan `mwccarm.exe` children, fixed by Job Objects (`winproc.py`). — [pictochat notes/tooling.md](https://github.com/tangOS-decomps/pictochat-decomp/blob/main/notes/tooling.md)

### Inferences
- metroskrew could remove wibo overhead for FFC's ~45 min cold build and for permuter throughput, if it supports DSi 1.2p2 (build 1028). This needs checking.

### Gaps
- metroskrew's supported compiler versions and its speed relative to wibo were not verified (its GitHub page was not fetched, and web search found nothing).
- No data on incremental-link caching for mwldarm in DS projects.
